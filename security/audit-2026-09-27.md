# Security & Production-Readiness Audit — September 27, 2026

**Scope:** this repo (bhameed23-oss/dream-to-business-builder) and its live site at dreams.belvi.casa.
**Method:** the `ai-app-pitfall-check` scan (all 40 checks, P1-P40) plus the 13-layer production-readiness scorecard, both built from Matt Murphy / The Faction Group LLC's public research on common bugs in AI-built ("vibe-coded") apps — credited per that skill's own citation rules (see `credit` note at the bottom). Also checked against this account's own standing project rules (secret management, human approval gates, agent attribution — see `brain/shared/projects/SECURITY.md`).
**This is not a security certification or legal compliance review** (no SOC 2, HIPAA, GDPR, or ADA claim is made here).

## The short version

This app has almost no attack surface to begin with: it's a static HTML/CSS/JS site with no server, no database, no login, and no user accounts. Nothing typed into the form ever leaves the visitor's own browser (it's saved to that browser's `localStorage` and nowhere else). That rules out the large majority of the 40-item checklist by design, not by luck. The scan below confirms that, rather than assuming it.

**One real, fixable gap was found (and fixed in this same pass): the deployed site had no security response headers (CSP, etc.).** Everything else checked out clean or doesn't apply to a site with this shape.

## What was actually run

The full `ai-app-pitfall-check` scan script (P1-P30, plus the newer P31/P37/P38 checks) was run against this repository with ripgrep, and every hit was opened and read before being called clean or a finding — no result below is guessed.

## Findings

### Fixed in this pass

**P30 — No security headers / CSP.** The scan found no `_headers` file and no CSP/HSTS configuration anywhere in the repo. **Fix applied:** added `_headers` at the repo root (the same folder Cloudflare Workers serves as static assets — see `wrangler.jsonc`), setting `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and a `Permissions-Policy` that turns off camera/mic/geolocation (none of which this app uses). The CSP is written strictly (`script-src 'self'`, `style-src 'self'`) because a check of the actual HTML confirmed there are no inline `<script>`/`<style>` blocks and no `onclick=""`-style handlers anywhere in `index.html` or `app/index.html` — everything is wired up with `addEventListener` in `app.js`, so a strict policy won't break anything. **To verify:** after the next deploy, open the live site's DevTools console and confirm there are no CSP violation warnings (there shouldn't be any, given the check above, but a static-analysis pass is not the same as watching the real browser apply the real policy).

### Checked and clean

- **P1-P3 — Hardcoded secrets, public env vars, committed `.env` files.** None found. This app has no API keys or secrets of any kind — it doesn't call any external service.
- **P4 — Auth tokens in `localStorage`.** The app does use `localStorage`, but only to save the business profile someone filled out (name, goals, notes) so it's still there on their next visit — not an auth token, and it's never sent anywhere. Not a comparable risk to what this check is looking for.
- **P5-P9, P19-P29 — Payment handling, SQL injection, SSRF, open redirects, error leakage, tRPC, cron/webhook auth, JWTs, CORS, mass assignment, IDOR, service-role keys, raw SQL, HTML email injection, server env vars in client bundles.** All not applicable — there is no server, no database, no payment flow, and no API of any kind in this app.
- **P13 — Row-level security.** Not applicable; there is no database.
- **P16 — Images missing `alt` text.** Not applicable; the app has zero `<img>` tags (its only "image" is an inline SVG favicon).
- **P18 — CI config present.** Yes — `.github/workflows/deploy.yml` exists, and no single commit in this repo's history has touched 40+ files at once (checked against the last 200 commits).

### Not checked (needs a human, not code)

Per the skill's own step 4 ("ask about what code can't show"), most of these don't meaningfully apply to a static, backend-less, no-login site, but for completeness:
- **Backups / disaster recovery:** not applicable in the traditional sense — there's no database to back up. The entire "backup" is the GitHub repo itself plus each visitor's own browser storage (which was always understood to be non-durable and low-stakes: losing it means re-filling a form, not losing real data).
- **Monitoring/alerting on real user errors:** none is set up today. Given the app's size and lack of a backend, this is a "worth doing eventually" item rather than a blocker — see Recommendations.
- **Old domains/DNS:** not reviewed here; this would be a Cloudflare-account-level check across all projects, not specific to this repo.

## This project's own standing rules (from `brain/shared/projects/SECURITY.md`)

- **Secret management** ("API keys in `.secrets/.env` only, never in project files") — clean; this app has no secrets of any kind to manage.
- **Human approval gates** ("deploying to production, deleting data, modifying auth, anything irreversible") — this app has no destructive operations, no auth, and deploys only happen when Bilal runs the Cloudflare dashboard's Git integration or `wrangler` himself; nothing here deploys or destroys anything on its own.
- **Agent attribution** ("every commit includes agent identity") — already followed; every commit in this repo's recent history carries the required `Co-Authored-By` / session attribution lines.

## Recommendations (not blockers)

1. **Verify the new `_headers` file after the next deploy** (see above) — a quick DevTools console check.
2. **Consider basic uptime monitoring** (e.g., a free tier of UptimeRobot or Cloudflare's own analytics) now that the site is live, so a future outage is noticed rather than discovered by chance.
3. **If the public form ever grows to actually send data somewhere** (an export-to-email feature, an integration with the command center, etc.), this audit should be re-run at that point — a lot of this checklist becomes relevant again the moment a server or database enters the picture.
